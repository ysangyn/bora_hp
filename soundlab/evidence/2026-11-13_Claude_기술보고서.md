## 3. 현재 오디오 엔진

줄 번호는 `index.html` 기준이고, 해당 부분은 `code/audio_engine_excerpt.js`에 줄 번호와 함께 발췌했어요.

### 3-1. 신호 흐름 [확인]

```
[합성 빗소리 AU.rain] ─┐
[주전자 KT] ───────────┤
[잠드는 소리 SN] ──────┤
[시계 TK] ─────────────┤
[심포니 SYM] ──────────┼─► AU.out (마스터 게인) ─► AU.tone (저역통과) ─► 컴프레서 ─► 출력
[효과음·종] ───────────┤
[녹음: 유리창 비, 끓는 물] ┤
[녹음: 그 밖의 창밖 소리] ─► AMB.out(0.8) ─► AMB.lp(저역통과) ─► AMB.lim ─┘

[노래 <audio>] ─────► 출력   (Web Audio를 거치지 않음)
[라디오 <audio>] ───► 출력   (Web Audio를 거치지 않음)
[프로젝터 유튜브 iframe] ─► 출력
```

- **마스터 게인** `AU.out`: 소리 켬 1, 끔 0. 잠들기 타이머가 돌면 `1 - smoothstep(진행률)`로 내려가요. (966, 973, 2071줄)
- **소리 빛깔** `AU.tone`: 저역통과, Q 0.3, 차단 주파수 `700 × 22^v` Hz (v는 0~1, 기본 0.7이면 약 6.1kHz). (1013줄)
- **마스터 컴프레서**: threshold -26dB, knee 14, ratio 4, attack 12ms, release 500ms. 리미터는 아니에요. (966줄)
- **창문 필터** `AMB.lp`: 창을 열면 16kHz, 닫으면 650Hz. (1037줄)
- **AMB.lim**: threshold -10dB, ratio 12. 현재 레벨에서는 거의 걸리지 않을 것으로 보여요 [추정].
- **노래와 라디오는 마스터 체인 밖이에요.** 컴프레서, 소리 빛깔, 클리핑 방지가 적용되지 않아요.

### 3-2. 재생과 중첩 [확인]

| 종류 | 방식 |

### 3-3. 음량 계산식 [확인]

녹음 침대 하나의 게인은 이렇게 정해져요. (`bedLevel` 1007줄, `ambUpdate` 1034줄)

```
게인 = 상황 레벨 × 흔들림 M × 잠들기 감쇠 fade × 사용자 막대 MX × 파일 상수 SF
```

- **상황 레벨**: 코드에 박힌 수. 예) 가벼운 비 `(0.4×(1-h)+0.12) × rs`.
- **흔들림 M**: 6초마다 ±0.15씩 무작위로 걷는 값, 0.5~1.25. 시정수 3~6초로 따라가요.
- **fade**: `1 - 잠들기 진행 × 0.6`, 심포니 중에는 0.7배.
- **MX**: '소리 섞기' 막대. 0.05~1.5의 **선형 배수**예요. 0.02 이하는 '끔'으로 처리해요. dB 눈금이 아니에요.
- **SF**: 파일마다 손으로 넣은 보정 상수.

비 세기는 세 단계예요. 부슬비, 보통 비, 장대비 순서로 `rain` 값 0.26 / 0.5 / 0.82, 배수 `rs` 0.34 / 0.62 / 1.

**'부드러운 소리'가 기본이에요** (`SOFT=true`, 1025줄). 이때는 비·거리·차·새·사이렌 녹음을 쓰지 않고 합성 빗소리와 합성 주전자만 써요.

### 3-5. 숨 고르기와 집중 모드 [확인]

- **숨 고르기** (`openPlant`, 1389줄): 10초 주기(5초 들이쉬고 5초 내쉬기)의 화면 안내예요. 소리는 선택 사항이고, 핑크 잡음을 220Hz 고역통과와 900Hz 저역통과에 걸고 0.1Hz LFO로 세기와 차단 주파수를 흔들어요. 생체 신호는 재지 않아요.

### 4-5. 측정에서 눈에 띈 점

1. **`light-rain`의 크레스트가 37dB예요.** 평균은 아주 작은데 피크가 -0.8dBFS까지 올라가요. 파일 안에 튀는 소리가 있다는 뜻이고, SF 1.8배를 곱하면 그 순간이 0dBFS를 넘어요.
2. **`music/01.mp3`의 트루피크가 +2.2dBFS예요.** 파일 자체가 피크를 넘겨 마스터링돼 있어요. 게인 0.407 덕에 재생에서는 문제가 없을 것으로 보여요 [추정].
3. **`dog-barking`, `tuning-radio`는 코드 어디에서도 쓰이지 않아요.**
4. **SF 상수는 일관된 기준이 없어요.** 적용 뒤 값이 -26에서 -36 LUFS까지 10 LU 넘게 흩어져 있어요.
5. **음원의 출처와 이용 조건이 저장소에 기록돼 있지 않아요.** 녹음 13개가 어디서 왔는지 확인이 필요해요.

| C. 부드러운 전환 | 있음 | 크로스페이드, 서서히 켜고 끄기 |
| C. 바이노럴 보존 | 해당 없음 | 바이노럴 음원 자체가 없음 |
| C. 출력 환경 고려 | 없음 | 헤드폰·스피커 구분 없음 |
| D. 소음 마스킹 | 재료만 있음 | 핑크·브라운 잡음이 있으나 외부 소음에 맞춘 조절은 없음 |
| 디지털 영양제 메뉴 | **없음** | |

**지금 있는 '목적별' 규칙** [확인]

- 잠들기 타이머가 돌면 전체 음량이 내려가고, 시계는 먼저 사라져요.
- 사용자 쪽 시각이 21시~6시면 새소리를 끄고 거리 소리를 줄여요.
- 잠드는 소리를 켜면 노래·라디오·빗소리를 꺼요. 심포니는 노래·라디오와 함께 켜지지 않아요.
- 사이렌은 '실제 녹음 소리'에서 창을 열었을 때만, 잠들기 중이 아닐 때만 드물게 나요.
- '지금에 맞게 알아서'는 시각과 기온으로 재료를 골라요.

이 규칙들은 측정값이 아니라 제 판단으로 넣은 수예요. 요청 문서가 지적한 "임의로 배합 비율을 정하는 방식"이 맞아요.

## 6. 디지털 영양제 통합 시 변경 범위

코드와 음원을 받지 못했으므로 일반적인 예상만 적어요.

| 영역 | 필요한 일 | 크기 |
|---|---|---|
| 재생 경로 | **전용 버스 신설.** 지금 마스터 체인(저역통과, 컴프레서)을 지나면 좌우 채널 신호가 바뀌어요. 바이노럴 음원은 이 체인을 우회해 출력에 직접 연결해야 해요 | 중 |
| 단독 청취 | 다른 소리를 모두 끄고 복원하는 기능. `holdMusic`/`resumeMusic`과 `mixApply`를 넓히면 돼요 | 소 |
| 메뉴와 화면 | 방 안의 입구(소품)와 패널 하나. 10종 선택, 최대 3종 블렌딩, 시간, 음량 | 중 |
| 음원 적재 | 파일이면 `sound/`와 같은 방식, 합성이면 모듈로. 10종의 길이와 형식에 따라 용량이 달라져요 | 미정 |
| 출력 환경 안내 | 헤드폰 필요 여부 표시. 휴대폰 스피커와 일부 블루투스 스피커는 모노라 바이노럴이 성립하지 않아요 | 소 |
| 백그라운드 재생 | 화면이 꺼져도 이어지게 하려면 `<audio>` 요소 재생이나 별도 처리가 필요해요 | 중~대 |

**기술적으로 미리 확인할 것**

- 마스터 컴프레서는 채널을 묶어서 누르지만, 그 앞의 저역통과가 반송파를 깎을 수 있어요. 차단 주파수가 최저 700Hz라서 그 아래 반송파는 남아요 [계산]. 그래도 전용 버스가 안전해요.
- MP3 인코딩은 설정에 따라 좌우 채널을 합쳐 부호화해요. 좌우 주파수 차가 보존되는지는 파일을 재 봐야 알아요.

**이름과 표현에 대한 의견**

요청 문서의 원칙(효능을 주장하지 않는다)에 동의해요. 다만 지금 사이트는 의학 용어를 쓰지 않는다는 원칙을 지켜 왔는데, 몇 가지가 그 원칙과 부딪혀요.

- '영양제', '아이 리프레시', '헤드 리셋', '바디 릴랙스'는 이름만으로 몸에 작용한다는 인상을 줘요. 설명에서 부정해도 이름이 먼저 읽혀요.
- 건강 효과로 읽힐 수 있는 표현은 광고·표시 규정에 걸릴 수 있어요. 저는 법률 전문가가 아니니, 공개 전에 확인을 권해요.
- 바이노럴 비트의 연구 결과는 엇갈려요. ChatGPT 쪽의 근거 검토가 여기서 가장 중요해요.

## 7. 공통 블렌딩 엔진의 모듈화 가능성

**가능해요. 다만 지금 코드는 그대로 떼어 낼 수 없어요.**

지금 엔진은 화면 상태(`S`), 저장(`LS`), DOM과 한 파일 안에서 얽혀 있어요. `ambUpdate` 하나가 날씨, 창문, 시각, 잠들기, 심포니를 모두 읽어요.

**제안하는 구조**

| 층 | 하는 일 | 실행 위치 | 맡을 쪽 |
|---|---|---|---|
| 1. 분석기 | 음원 파일 → 특성 JSON (LUFS, 피크, 대역, 돌발음 등) | 오프라인 (Python/Node), CI | ChatGPT 설계, 양쪽 검증 |
| 2. 규칙 엔진 | `(음원 특성, 목적, 사용자 막대, 상황) → (재료별 게인, 필터 값)` 을 돌려주는 **순수 함수** | 브라우저와 Node 양쪽 | ChatGPT 설계, Claude 통합 |
| 3. 재생 어댑터 | 규칙 엔진의 결과를 Web Audio 노드에 적용 | 브라우저 | Claude |

- 2층이 DOM과 오디오 노드를 모르는 순수 함수라면, 같은 입력에 같은 출력이 나오는지 Node에서 시험할 수 있어요. 두 AI가 같은 시험 결과를 볼 수 있는 핵심이에요.
- 1층의 출발점으로 `code/sound_manifest.json`을 만들어 두었어요. 지금 코드의 상수와 이번 측정값을 한 파일에 모은 거예요.
- 사용자 수동 조절은 2층의 입력으로 그대로 들어가고, 자동 추천값은 별도 필드로 돌려주면 둘이 구분돼요.

**먼저 정해야 할 것**

- 목표 음량의 기준 (예: 재료별 목표 LUFS, 합산 상한)
- 합성음의 측정 방법 (OfflineAudioContext 렌더링)
- 노래·라디오를 마스터 체인에 넣을지 여부. 넣으면 CORS와 백그라운드 재생에 영향이 있어요.

## 8. 두 AI의 협업 방법

**권하는 방식: GitHub 저장소 하나를 공통 기준으로.**

1. **브랜치**: `sound-lab` 브랜치에서 작업해요. `main`은 자동 배포되므로 실험을 넣지 않아요.
2. **폴더**: `soundlab/` 아래에 분석기, 규칙 엔진, 시험, 문서를 둬요. `firebase.json`의 ignore에 넣으면 배포에서 빠져요.
3. **공통 자료**: `sound_manifest.json`(음원 특성), 시험 벡터(입력과 기대 출력), 측정 스크립트.
4. **같은 시험 결과**: GitHub Actions에서 시험을 돌리면 결과가 저장소에 남아 양쪽이 같은 것을 봐요.
5. **결정 기록**: `soundlab/DECISIONS.md`에 무엇을 왜 정했는지, 근거가 연구인지 가설인지 측정인지 표시해 적어요.
6. **검증 분리**: 한쪽이 만든 것을 다른 쪽이 PR에서 검토해요.

**전달 경로**

- 저장소 `ysangyn/bora_hp`는 공개 상태예요 [확인]. ChatGPT는 주소(https://github.com/ysangyn/bora_hp)로 코드를 읽을 수 있어요. 공개 저장소이므로 노래 MP3 5개도 이미 누구나 받을 수 있는 상태라는 점은 알아 두세요.
- 두 AI가 직접 대화하는 통로는 필요하지 않아요. 저장소와 PR이 통로 역할을 해요.
- 저는 이 저장소에 푸시할 수 있어요. ChatGPT가 푸시할 수 없다면 ChatGPT의 결과물을 받아 제가 브랜치에 올리는 방식이 돼요.
