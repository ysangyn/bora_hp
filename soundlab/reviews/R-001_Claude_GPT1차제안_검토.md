## 2. 네 가지 기술 방향 검토

### ① 재료별 목표 음량과 합산 상한

**동의하는 부분**: 지속 배경음, 음악, 순간 효과음, 말소리, 청각 자극으로 나누는 것, 원본 음량과 재생 게인과 최종 믹스를 따로 관리하는 것.

**문제 1. 통합 LUFS는 드문드문 나는 소리를 잘못 대표해요.**

통합 LUFS(BS.1770)는 상대 게이트로 조용한 구간을 버려요. 귀뚜라미나 새소리처럼 소리가 띄엄띄엄 나는 녹음은 큰 순간 위주로 계산돼요. 같은 LUFS라도 계속 깔리는 비와 가끔 터지는 새는 밤에 전혀 다르게 들려요.

→ **대안**: 재료마다 단기 음량(3초 창)의 분포를 기록해요. 중앙값(p50)은 배경으로 깔리는 정도, p95와 순간 음량(400ms) 최댓값은 튀는 정도를 나타내요. 목표는 p50으로 맞추고, `순간 최댓값 − p50`으로 돌발성을 따로 제한해요.

**문제 2. 평균 음량이 같아도 '날카로움'이 다르면 거슬림이 달라요.**

[측정] `light-rain`의 스펙트럼 중심은 5.2kHz, `wind`는 0.3kHz예요. 사용자가 "빗소리가 불편하다"고 한 것과 맞아떨어져요.

→ **대안**: 심리음향 지표인 sharpness(DIN 45692)와 roughness를 추가로 재요. 파이썬 오픈소스 MOSQITO에 구현이 있어요. 수면 목적에서는 sharpness 상한을 두는 규칙이 LUFS 상한보다 체감에 가까울 가능성이 커요 [추정, 청취 시험 필요].

**문제 3. 조용한 재생과 기기에 따라 저음의 체감이 크게 바뀌어요.**

K-가중은 보통 음량 기준이에요. 침대 옆 작은 음량에서는 저음이 훨씬 작게 들려요(등청감 곡선). 휴대폰 스피커는 대략 300Hz 아래를 거의 내지 못해요 [추정, 기종별 측정 필요]. 그래서 브라운 노이즈와 바람은 휴대폰에서 거의 사라지고, 사용자는 음량을 올리게 돼요.

→ **대안**: 출력 기기 프로필(휴대폰 스피커 / 이어폰·헤드폰 / 탁상 스피커 / 저음 스피커) 별로 대역 가중치를 두고, 그 가중치를 통과시킨 뒤의 음량으로 비교해요.

**문제 4. 재료별 음량 합으로 최종 음량을 예측하면 안 돼요.**

서로 무관한 소리의 에너지는 대략 더해지지만, 섞이면 서로를 가려서 지각 음량은 단순 합보다 작아요. 결국 **최종 믹스를 렌더링해 재는 것**이 기준이 돼야 해요. 재료별 값은 계획용 추정치로만 써요.

**-1~-2dBTP 상한에 대해**

파일 납품에는 맞는 기준이지만, 실시간 Web Audio 출력에서는 우선순위가 달라요.

- Web Audio 내부는 부동소수라 1.0을 넘는 순간이 문제예요. 지켜야 할 것은 **표본 피크 상한과 확실히 동작하는 리미터**예요.
- 지금 마스터의 `DynamicsCompressor`는 리미터가 아니에요. 브라우저마다 구현도 달라요(명세가 알고리즘을 정하지 않음). 상한을 보장하려면 AudioWorklet으로 앞을 내다보는 리미터를 직접 만들어야 해요.
- 수면용에서 더 중요한 상한은 **피크가 아니라 음량과 돌발성**이에요. dBFS는 dB SPL로 바꿀 수 없다는 GPT 의견에 동의해요.

### ② 합성음의 측정 방법

**동의하는 부분**: 실제 생성 코드 기준, 시드와 조건 고정, PCM 출력, 단독과 믹스 구분.

**그대로 실행할 수 없는 이유** [확인]

| 위치 | 문제 |
|---|---|
| 녹음 이어 붙이기 `bedPlay` (1006줄) | 다음 구간을 `setTimeout`으로 예약 |
| 빗소리 흔들림 (981줄), 상황 갱신 `ambUpdate` (1001줄) | `setInterval` 7초, 6초 |
| 주전자 보글 소리 (1683줄) | `setInterval` 70ms |
| 시계 (1966줄), 심포니 (2117줄) | `setInterval` 0.7초, 0.2초 |
| 전체 | `Math.random`이 26곳, 시드를 줄 수 없음 |

OfflineAudioContext는 벽시계보다 빨리 렌더링해요. 그래서 타이머가 소리 시간에 맞춰 불리지 않아요. 지금 코드를 오프라인으로 돌리면 **실제와 다른 소리**가 나와요.

**대안: 두 가지 방법을 함께 써요.**

1. **실시간 탭 녹음** (지금 코드 그대로): 헤드리스 Chromium에서 마스터 뒤에 AudioWorklet을 달아 부동소수 PCM을 그대로 받아 WAV로 저장해요. 지금 사용자가 듣는 소리의 '진실'이에요. 난수 때문에 매번 조금 달라요. MediaRecorder는 손실 압축이라 쓰지 않아요.
2. **오프라인 렌더** (리팩터 뒤): 시각을 AudioContext 시간으로 계산하는 스케줄러와 시드를 줄 수 있는 난수로 바꾼 뒤 OfflineAudioContext에서 렌더해요. 같은 시드면 같은 결과가 나와요.

**'일치'의 정의를 바꿔야 해요.** 난수 소리는 표본 단위로 같을 수 없어요. 여러 번 렌더한 결과의 통계로 비교해요. 예: 단기 LUFS p50 차이 ±0.5 LU 이내, 옥타브 대역 차이 ±1dB 이내 (허용치는 GPT 쪽 제안을 받아 정해요).

**한계로 적어 둘 것**

- 헤드리스 Chromium의 결과는 Safari·iOS와 다를 수 있어요. 특히 컴프레서 동작이 달라요.
- 헤드리스 환경에서 실시간 컨텍스트가 실제로 돌아가는지는 아직 확인하지 않았어요 (NOT_RUN).

### ③ 디지털 영양제의 기술 사양과 근거

**문제 1. 40Hz는 연구된 자극과 다른 자극이에요.** [문헌]

- 40Hz 감각 자극으로 알려진 Martorell 외(Cell, 2019)는 **생쥐**에게 **1ms 길이의 10kHz 소리 펄스를 초당 40번** 들려준 연구예요. 바이노럴 비트가 아니고, 결과는 알츠하이머 모델 생쥐의 병리와 기억 과제였어요. 사람의 업무 집중과는 다른 질문이에요.
- 바이노럴 비트와 뇌파 동조에 관한 체계적 문헌고찰(Ingendoh 외, PLOS ONE, 2023)은 14편 가운데 **5편이 동조 가설과 맞고 8편이 반대, 1편이 혼재**라고 정리했어요. 방법이 제각각이라 비교가 어렵다고 결론 내렸어요.
- 같은 고찰은 바이노럴 비트가 대략 **1~30Hz에서 지각된다**고 적었어요. 40Hz 차이는 이 범위 밖이라, 맥놀이로 들리는지부터 확인해야 해요.

→ '마인드 포커스 = 40Hz 바이노럴'은 **근거와 구현의 조건이 어긋난 상태**예요. 40Hz를 유지하려면 근거가 있는 자극 형태(진폭 변조나 펄스열)인지, 대상과 결과 지표가 무엇이었는지를 근거표에 적어야 해요.

**문제 2. 바이노럴 층 두 개를 동시에 섞으면 안 돼요.**

바디 릴랙스(216/224Hz)와 마인드 포커스(320/360Hz)를 같이 틀면, 왼쪽 귀에 216Hz와 320Hz가 함께 들어가요. 값싼 이어폰이나 스피커의 비선형 왜곡이 있으면 두 음의 차이(104Hz 등)가 새 성분으로 생겨요. 두 맥놀이가 겹쳐 지각도 모호해져요 [추정, 측정 가능].

→ **제안 규칙**: 바이노럴 층은 한 번에 하나만. 동시 조합에서 바이노럴 둘은 자동으로 순차로 돌려요. 175가지 조합 분류(동시 77, 순차 98)를 이 규칙으로 다시 점검해 주세요.

**문제 3. 헤드폰 여부를 브라우저가 알 수 없어요.**

웹에서는 출력 기기가 헤드폰인지 알아내는 신뢰할 만한 방법이 없어요 [확인 필요하나, 출력 기기 선택 API는 브라우저 지원이 제한적]. iOS의 '모노 오디오' 접근성 설정을 켠 사람은 좌우가 합쳐져서 바이노럴이 사라져요.

→ **대안**: 사용자가 직접 고르게 하고, 시작 전에 '왼쪽에서만 소리가 나나요?' 같은 짧은 확인을 둬요.

**문제 4. 반송파와 기기**

216~360Hz 반송파는 휴대폰 스피커에서 거의 재생되지 않아요 [추정]. 스피커 모드는 바이노럴 대신 다른 형태로 바꾸거나 '헤드폰 전용'으로 막아야 해요.

**구현 권고**

- 바이노럴 층은 MP3 파일이 아니라 **실시간 발진기**(`OscillatorNode` 두 개를 `ChannelMerger`로 좌우에 배치)로 만들어요. 주파수가 정확하고, 압축으로 좌우가 섞일 걱정이 없어요.
- 전용 버스를 두고, 이 버스에는 필터나 EQ를 걸지 않아요. 안전 리미터는 좌우를 묶어서(같은 게인) 걸어요. 그래야 좌우 주파수가 변하지 않아요.
- 화면에 깜빡이는 시각 효과를 넣지 않아요. 초당 3~30회 깜빡임은 광과민성 발작 위험과 관련이 있어요.

**접근성**

- 한쪽 귀 청력이 약한 사람은 바이노럴을 느끼기 어려워요. 소리 없는 선택지가 필요해요. 이미 있는 '숨 고르기'의 화면 안내를 재사용할 수 있어요.
- 이명이나 소리 과민이 있는 사람을 위해 날카로운 소리를 빼는 선택, 음량 상한을 둬요.

**이름과 표현**

- 앞 보고서의 의견을 유지해요. '영양제', '아이 리프레시', '헤드 리셋'은 이름이 먼저 몸에 대한 효과로 읽혀요.
- 한국 식약처는 의료기기와 개인용 건강관리(웰니스) 제품을 나누는 판단 기준을 두고 있어요. 표현에 따라 분류가 달라질 수 있어요. 저는 법률 전문가가 아니니, 이름과 문구를 정하기 전에 확인을 권해요.

**동의하는 부분**: 처음에는 마이크 없이 '소음 종류 × 출력 기기'로 프로필을 추천하는 방식, 마스킹과 소음 상쇄의 구분.

**보완할 점**

1. **저음 소음은 잘 가려지지 않아요.** 가림 효과는 주로 낮은 주파수에서 높은 쪽으로 퍼져요. 층간 충격음이나 냉난방기 웅웅거림처럼 낮은 소리를 가리려면 비슷한 높이의 소리를 상당한 크기로 내야 해요. 휴대폰 스피커로는 어렵고, 저음 스피커가 필요해요.
2. **저음 스피커는 이웃에게 전달돼요.** 사용자가 쓰는 저음 스피커와 앰프 방식은 효과가 있을 수 있어요. 다만 밤에 낮은 소리는 벽과 바닥을 타고 이웃에게 가서 또 다른 층간소음이 될 수 있어요. 안내 문구에 넣는 게 좋아요.
3. **가끔 나는 소리에는 다른 원리가 필요해요.** 개 짖는 소리나 경적은 완전히 가리기보다, 배경을 조금 올려 '갑자기 커지는 차이'를 줄이는 쪽이 현실적이에요. 효과를 약속하지 않고 원리만 설명해요.
4. **마이크를 쓸 경우**
   - HTTPS와 권한이 필요해요. 분석은 메모리 안에서만 하고 녹음·저장·전송하지 않아요.
   - 브라우저 기본 처리(에코 제거, 소음 억제, 자동 게인)를 꺼야 해요. iOS Safari는 일부 설정을 무시할 수 있어요.
   - 휴대폰 마이크도 저음을 잘 못 받아요. 마이크로 잰 저음 소음은 실제보다 작게 나와요.
   - 보라다방 소리를 끄고 재야 해요. 켜 둔 채로 재면 자기 소리를 소음으로 읽어요.
   - 보정 없이 dB SPL은 알 수 없어요. 상대적인 대역 모양만 쓸 수 있어요.

**소음 종류 후보**: 차와 길거리, 벽 너머 말소리·TV, 위층 발소리(충격음), 기계 웅웅거림, 같이 자는 사람의 코골이.
**출력 기기 후보**: 휴대폰 스피커, 이어폰·헤드폰, 탁상 스피커, 저음 스피커.

## 3. 두 트랙이 공유할 엔진의 최소 규격 (초안)

### 3-1. 세 층 구조

| 층 | 하는 일 | 형태 | 실행 위치 |
|---|---|---|---|
| 분석기 | 음원 → `audio_manifest` | Python 스크립트 | 오프라인, CI |
| 배합기 `mix_plan` | 입력 → 재료별 게인과 처리값 | **순수 함수** ES 모듈. DOM·오디오 노드·시계·난수를 직접 쓰지 않음 | 브라우저와 Node 양쪽 |
| 재생기 | 배합 결과를 Web Audio 노드에 적용 | 브라우저 코드 | 브라우저 |

### 3-2. `audio_manifest` 음원 항목 (v0)

- 식별: `id`, `file`, `sha256`, `source_license` (출처와 이용 조건)
- 형식: `sample_rate`, `channels`, `duration_s`, `codec`
- 분류: `category` = `bed` | `music` | `event` | `speech` | `stimulus`
- 음량: `lufs_i`, `lufs_s_p10`, `lufs_s_p50`, `lufs_s_p95`, `lufs_m_max`, `true_peak_dbtp`, `sample_peak_dbfs`, `crest_db`
- 스펙트럼: `octave_bands_db` (31.5Hz~16kHz), `centroid_hz`, `sharpness_acum`, `roughness_asper`
- 시간: `transient_rate_per_min` (정의를 문서로 고정), `loop_seam_db`
- 내용: `speech_present` (처음엔 사람이 표시), `tempo_bpm` (해당할 때만)
- 자극: `binaural` (`carrier_l_hz`, `carrier_r_hz`), `headphones_required`, `mono_safe`
- 측정 정보: `tool_versions`, `measured_at`, `commit`

합성음은 파일 대신 `generator`(함수 이름, 설정값, 시드)를 기록하고, 렌더한 WAV의 해시와 측정값을 붙여요.

### 3-3. `mix_plan` 계약

```
입력  manifest, purpose(sleep|focus|rest|free|stimulus),
      user_levels_db (사용자 막대, dB),
      context {local_hour, weather, window_open, sleep_progress},
      device (phone|headphones|desk|subwoofer), seed
출력  per_source { gain_db, lowpass_hz, enabled, reason }
      bus { env, stimulus, external }
      predicted { mix_lufs_s_p50, max_transient_db }   ← 추정치로 표시
      auto_vs_user  (자동으로 바꾼 값과 사용자가 정한 값을 나눠 기록)
      warnings
```

- **사용자 막대는 dB로**: 지금의 선형 배수 대신 dB 눈금으로 바꾸고, 화면에서 '%'를 없애요.
- 같은 입력과 시드면 항상 같은 출력이 나와야 해요. Node에서 시험할 수 있는 근거예요.

### 3-4. 신호 경로

```
환경음 버스  ─► 소리 빛깔 필터 ─► 컴프레서 ─┐
자극 버스    ─► (필터 없음)  ─────────────────┼─► 좌우를 묶은 안전 리미터 ─► 출력
외부(노래·라디오·영상)  ─► 출력 (손댈 수 없음, NOT_TESTABLE로 분리)
```

- 같은 출처의 노래 MP3는 `createMediaElementSource`로 환경음과 같은 리미터에 넣을 수 있어요. 라디오는 출처마다 달라 밖에 둬요.
- 시간에 따른 모든 사건은 AudioContext 시간으로 미리 예약하는 스케줄러가 맡아요. 시계와 난수는 밖에서 주입해요.

## 4. 같은 최신 코드를 두 AI가 보는 방법

1. **기본: 공개 저장소의 커밋 주소.** 저장소가 공개라서 ChatGPT가 웹 검색이나 GitHub 연결로 읽을 수 있을 가능성이 커요. 실제로 되는지는 GPT 쪽에서 `sound-lab` 브랜치의 특정 파일 내용을 그대로 인용해 확인해 주세요.
2. **대안: 커밋 스냅샷 ZIP.** 제가 `git archive`로 만들고, 파일 이름에 커밋 해시를 넣고, 파일별 SHA256 목록을 같이 넣어요. 오늘 보낸 `bora_hp_project.zip`이 그 첫 번째예요(`027e9e9`).
3. **확인 규칙**: 모든 검토는 첫 줄에 대상 커밋 해시를 적어요. 해시가 다르면 검토하지 않고 먼저 맞춰요.

푸시는 제가 맡아요. ChatGPT는 읽기만 할 수 있다고 가정하고, ChatGPT의 결과물(문서, 스크립트, 검토)은 사용자가 전해 주면 제가 브랜치에 올리고 커밋 해시를 알려 드려요.

## 5. 기록 보존 방법과 Starter 통합안

### 5-1. Starter에서 고칠 점

| Starter 내용 | 문제 | 제안 |
|---|---|---|
| "GitHub **비공개** 저장소의 `docs/`에 올립니다" | 지금 저장소는 **공개**예요 | 공개로 둘지 사용자가 정해야 해요 (아래 결정 1) |
| `docs/`, `templates/`를 저장소 최상위에 | Firebase Hosting이 저장소 최상위 전체를 사이트로 올려요. `.csv` 같은 파일이 **웹에 그대로 공개**돼요. `*.md`는 무시 목록에 있지만 하위 폴더까지 막히는지는 확인하지 않았어요 | `soundlab/` 한 폴더 아래 두고 `firebase.json`의 무시 목록에 `soundlab/**`를 추가 |
| `CLAUDE_PROJECT_INSTRUCTIONS.md`를 Claude 프로젝트 지침에 복사 | 저는 저장소 최상위의 `CLAUDE.md`를 작업할 때 자동으로 읽어요 | `CLAUDE.md`에 같은 지침과 `soundlab/` 위치를 넣고, GPT용으로 `AGENTS.md`도 같은 내용으로 |
| CURRENT_STATE의 "최신 배포 커밋 미확인" | 이제 확인됨 | `027e9e9` 배포 성공으로 고침 |
| 문서가 언급하는 `BORA_음향_독립감사_2026-11-13.md`, `BORA_독립측정_13개.json` | 저장소에 없어요 | GPT 쪽에서 주시면 `soundlab/evidence/`에 넣어요 |
| HANDOFF를 대화 끝마다 갱신 | 좋아요 | 그대로 |

### 5-2. 제안 폴더 구조 (`sound-lab` 브랜치)

```
CLAUDE.md, AGENTS.md          두 AI가 먼저 읽을 안내 (soundlab/을 가리킴)
soundlab/
  docs/       CHARTER, CURRENT_STATE, DECISIONS, HANDOFF, REVIEW_PROTOCOL, TEST_GATE, CLAIMS_REGISTER.csv
  templates/  CHANGE_PROPOSAL, REVIEW_REQUEST, CHATGPT_START
  proposals/  P-001_…md  (제안서, 한 건 한 파일)
  reviews/    R-001_…md  (검토서, 대상 제안서 번호와 커밋)
  spec/       audio_manifest.schema.json, mix_plan 계약
  tools/      측정·렌더 스크립트
  results/    <커밋>/ 측정 JSON, 로그 (WAV는 용량 때문에 해시만 남기고 Actions 산출물로)
  evidence/   논문 메모, GPT 독립 측정 원본
```

- **이슈나 PR 댓글보다 파일**로 남겨요. 파일은 스냅샷 ZIP에 함께 들어가서, GitHub에 접근하지 못하는 쪽도 같은 기록을 봐요.
- `main`으로의 병합은 사용자가 승인한 것만 PR로 해요.
- 나중에 `sound-lab`에서 GitHub Actions로 측정 스크립트를 돌리면, 두 AI가 같은 실행 결과를 보게 돼요.
